1. What STOS Studio does

STOS BASIC (STOS: The Game Creator, Mandarin/Jawx 1988) only understands numbered program lines, typed into its own editor on the Atari ST. STOS Studio lets you write those programs in Visual Studio Code instead, in a friendlier form, and run them in the Hatari emulator with one click:

  • No line numbers. Jump to @labels instead, split big programs over several files with #include, indent your code, and keep notes that STOS never sees.
  • Help on every STOS command (about 360): suggestions while you type, and help when you rest the mouse on a command, with its syntax, an explanation, an example and the page of the STOS manual.
  • Colours for commands, functions, strings, numbers, comments and labels, plus a few ready-made pieces of code (snippets).
  • Build turns your .stos file into the numbered .asc file that STOS loads. Any mistakes (unknown labels, missing files, characters the Atari does not have) are all listed at once.
  • Red squiggles underline those mistakes right in the editor, and list them in VS Code's Problems panel, as soon as you save.
  • Run builds, gets an emulated hard disk ready with your STOS and your program on it, and starts Hatari.

STOS Studio was written from scratch, inspired by Neil Halliday's STOS: The Game Creator extension (stoscoders.com/visual-studio-code). It contains no code or text from it. See chapter 14 for the credits.

3. Installing

STOS Studio comes as one file, stos-studio-0.1.1.vsix.

Download it from the Releases page of the project on GitHub (github.com/dimfilhub/STOS-Studio). In VSCodium-style editors it is also on Open VSX.

  1. Remove any other STOS extension first. Two extensions that both handle .stos files get in each other's way. In VS Code open the Extensions view (ShiftCmdX), find the other STOS extension and choose Uninstall.
  2. In the Extensions view, click the ··· menu at the top and choose Install from VSIX..., then pick stos-studio-0.1.1.vsix.
    Or, in a terminal: code --install-extension stos-studio-0.1.1.vsix --force
  3. Reload any VS Code windows that were open: Command Palette (ShiftCmdP), Developer: Reload Window.

To update later, install the new .vsix the same way; your settings stay.

On Windows and Linux use Ctrl where this manual says Cmd.

4. First-time setup

Tell STOS Studio where your Hatari, TOS image and STOS are. Open the Command Palette (ShiftCmdP), type STOS Studio, and run these three commands:

CommandWhat to pick
STOS Studio: Select Hatari...On macOS pick Hatari.app itself; STOS Studio finds the program inside it. On Windows pick hatari.exe.
STOS Studio: Select TOS image...Your TOS ROM image file (.img, .rom or .tos).
STOS Studio: Select STOS folder...The folder that contains BASIC208.TOS. Picking the folder around it also works: STOS Studio looks for a STOS folder inside.

Each choice is saved in your user settings, so you do this only once for all projects. A message confirms what was saved. You can check or change the values any time in Settings (Cmd,), section STOS Studio.

If a project has its own .vscode/settings.json with a different value, that value wins for that project. STOS Studio warns you when this happens.

5. Your first project

  1. Command Palette, STOS Studio: New STOS project...
  2. Choose the folder to create the project in (for example a folder STOSProjects in your home folder).
  3. Type a name, for example MyFirstGame. Names cannot contain \ / : * ? " < > | and cannot start with a dot.

The project opens (in a new window if one was already open). It contains:

FileWhat it is
main.stosyour program: a small "Hello" to start from
.vscode/settings.jsonthe project's settings (main file, output file, emulated drive)
.gitignoretells git to skip the built files and the emulated drive

After the first Build and Run two more folders appear: stos/ with the built main.asc, and hatari/hd/, the emulated hard disk (drive C: for the Atari).

The new main.stos looks like this:

' main.stos - a new STOS Studio project
' Lines starting with ' are notes for you: STOS never sees them.
' Build: Shift+Cmd+B (Ctrl+Shift+B).  Run in Hatari: the play button at the top right.

mode 0 : cls : curs off : hide on
colour 0,$000 : colour 1,$777 : pen 1 : paper 0
gosub @title
wait key
default
end

' prints the title in the middle of the screen
@title
locate 0,10 : centre "Hello from STOS Studio!"
locate 0,12 : centre "Press a key"
return

Press the play button at the top right of the editor to build it and run it in Hatari (chapter 9).

6. Writing .stos files

A .stos file is ordinary STOS BASIC without line numbers. Build adds the numbers. Here is the idea in one example:

' a note for you: lines starting with ' or // never reach STOS
#include "sprites.stos"
mode 0 : cls
@loop
   print "Hello"
   if inkey$="" then goto @loop

Build turns it into (assuming sprites.stos holds one line):

10 sprite 1,10,10,1
20 mode 0 : cls
30 print "Hello"
40 if inkey$="" then goto 30

Line numbers

  • Lines are numbered 10, 20, 30, ... in the order they appear.
  • #lineinc 5 on a line of its own changes the step for the lines after it (1 to 1000).
  • The highest line number is 65535.
  • Do not type line numbers yourself: a line that starts with a digit is reported as an error.

Labels

  • A label is @ followed by letters, digits and _: @main_loop, @level2. Upper and lower case do not matter: @Loop is @loop.
  • At the start of a line, a label marks that line. Anything after it stays as the line's code: @loop print X becomes 120 print X.
  • A label alone on a line marks the next line that has code. Several labels may mark the same line.
  • Everywhere else, @name is replaced by the number of its line, wherever STOS expects a line number: goto @loop, gosub @title, if X then @hit else @miss, on N goto @a,@b,@c, restore @levels, on error goto @oops, ...
  • Labels are whole names: @a never changes part of @ab.
  • Not replaced: inside "strings", after rem, and when @ comes straight after a letter or digit.

Several files

  • #include "file.stos" on a line of its own inserts another file at that point. The path is relative to the file that contains the #include. Included files may include others.
  • Labels work across files: define @beep in one file, gosub @beep in another.

Comments, blank lines and indentation

  • Lines starting with ' or // are notes for you. Build drops them, so they use no line numbers and no memory on the Atari. Cmd/ turns lines into such notes and back.
  • rem lines are STOS comments: they are kept, and STOS lists them.
  • Blank lines and indentation are only for you; Build removes them.

Letters with accents

The Atari has its own character set. Build writes your text in it, so print "café" works. Characters the Atari does not have, such as € or emoji, are reported with their position.

7. Help while you write

Suggestions

While you type, VS Code suggests STOS commands. The icon shows what each one is: an instruction (sprite), a function (x mouse), or a reserved variable (timer). Press CtrlSpace to see suggestions at any time.

Help on a command

Rest the mouse on a command to see:

  • its syntax (all forms, as on the STOS reference card; [ ] means optional),
  • what it does, with a small example,
  • the page of the STOS User Guide (the page number of the PDF scan) where it is described.

Two-word commands work too (move x, reserve as screen), and the longest one wins: over default physic you get help for that, not for default. Nothing pops up inside strings or labels.

Colours

Commands, functions, control words (if, goto, for...), strings, numbers ($7F0, %1010, 3.5), comments, @labels and #include each get their own colour. The colours come from your VS Code colour theme.

Snippets

Type the word on the left and pick it from the suggestions to insert a ready-made piece of code; Tab jumps between the parts to fill in.

TypeInserts
fora for ... next loop
ifelsea one-line if ... then ... else
whilea while ... wend loop
repeata repeat ... until loop
suba labelled subroutine ending in return
gameloopscreen set-up and a main loop that runs until Esc
windopena text window with a border and a title

8. Building, and red squiggles

Red squiggles

You do not have to build to find out about mistakes. STOS Studio checks your whole project (the main file and everything it includes) and shows each mistake as a red wavy underline in the editor, exactly where it is. Rest the mouse on it to read the message.

@loop print "Hi"
   goto ⟦@lopp⟧ : rem unknown label: the label is @loop
  • The same messages are listed in VS Code's Problems panel (View, Problems, or ShiftCmdM) with the file and line. Click one to jump to it.
  • Where STOS Studio knows the exact characters, only those are underlined: the @lopp above, a € in a string, the digits of a line number you typed by hand. Other mistakes underline the whole line.
  • A mistake inside an included file is shown in that file, not in the main file.
  • The check runs when you open a project, each time you save a .stos file or change a STOS Studio setting, and when Build or Run starts. Fix the mistake and save, and the squiggle disappears.
  • The check reads the files as saved on disk, so a mistake you have just typed shows up only after you save.

Building

Build turns the project's main file (main.stos) into stos/main.asc.

  • Click the tools button at the top right of a .stos file, or
  • press ShiftCmdB and choose Build STOS program, or
  • run STOS Studio: Build from the Command Palette.

A terminal panel shows what happens:

Reading main.stos
Including sprites.stos
51 lines, 9 labels
Writing /Users/you/STOSProjects/MyFirstGame/stos/main.asc
Done.

If something is wrong, nothing is written and every problem is listed (up to 20) with file, line and column, so you can fix them all in one go. They also appear as red squiggles, as described above:

main.stos:12:7: unknown label @boss
levels.stos:3: label @start is already defined in main.stos:5
main.stos:20:11: character "€" (U+20AC) does not exist in the Atari ST character set
When STOS reports an error in a line number (for example "Syntax error in line 230"), open stos/main.asc to see which line that is, then find it in your .stos file.

9. Running in Hatari

Click the play button at the top right of a .stos file (or run STOS Studio: Build and run in Hatari). STOS Studio then:

  1. builds the program first, so you never run an old version;
  2. the first time only, copies your STOS folder onto the project's emulated hard disk (hatari/hd/STOS, about 5 MB). A drive that already has STOS is left alone, so older projects keep working;
  3. copies your program to the root of that disk as MAIN.ASC;
  4. starts Hatari with your TOS image and the disk as drive C:, and starts STOS from it.

STOS opens in its editor. Load your program and run it by typing:

load "C:\MAIN.ASC"
run

Hatari's messages appear in the terminal panel in VS Code. Close Hatari when you are done; the next Run starts it again with the newest version of your program.

Your own files: the assets folder

Put sprite banks, pictures and other files your program loads into a folder called assets in the project (sub-folders are fine). On every Run they are copied onto the emulated disk, next to MAIN.ASC, so the program can load them by name:

load "sprites.mbk"
  • Files you edit arrive again on the next Run. Names starting with a dot are skipped.
  • The Atari has short file names (8 letters, a dot, 3 letters). Longer names are copied but Run warns you.
  • Use another folder with stosStudio.assetsFolder; an empty setting copies nothing.

Optional: the sprite editor from STOS-Toolkit

STOS-Toolkit is a separate project with graphic tools written in Python. If you have it, run STOS Studio: Select Toolkit folder... once and pick its folder (the one with pyproject.toml and .venv). Two things then appear:

  • Right-click a .mbk or .spr file in the Explorer, then Open sprite editor (STOS-Toolkit).
  • The same command in the Command Palette: it opens the sprite bank that is open in VS Code, or a new bank.

The editor opens in its own window. Save the bank into your assets folder and the next Run copies it onto the emulated disk. Without a Toolkit folder these commands stay hidden and everything else works as before.

The emulated machine is set by three settings: stosStudio.machine (default STE), stosStudio.memory (default 1 MB) and stosStudio.resolution (default low resolution, 320 × 200 in 16 colours). See chapter 10.

10. Settings

Open Settings with Cmd, and search for STOS Studio. Paths may start with ~ for your home folder. Project paths are relative to the project folder.

Safety: the settings that name programs and folders on your computer (hatariPath, tosImage, stosFolder, toolkitFolder) can only be set in your own user settings, never by a project you download. outputFile and hardDrive must stay inside the project folder. Run and the sprite editor start external programs, so they are disabled until you trust the workspace (VS Code asks when you open a new folder).

13. A program to check everything: the spaceship

This program flies a small spaceship around the screen with the cursor keys. It uses labels with goto, gosub and on ... gosub, reads the cursor keys, and draws without flicker on a hidden screen. To try it, make a new project and replace main.stos with it.

Keys: cursor keys set the direction (the ship keeps going), Space stops, Esc quits.
